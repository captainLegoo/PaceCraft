# COROS 训练看板

基于 **COROS 官方 MCP**（`mcp.coros.com` 中国区）自建的本地训练看板。

**每个使用者各自部署，数据只存在自己的机器上，不经过任何第三方服务器。**
你自己的 COROS 账号、训练数据和 OAuth 凭证都与其他使用者完全隔离 ——
仓库里不含任何人的数据，也不需要（也无法）共用凭证。

---

## ⚠️ 这是单机工具，不要直接暴露到公网

**当前版本是单用户设计，服务只监听 `127.0.0.1`（回环地址）。**
每个人自己 clone、自己授权、自己跑。同一 WiFi 下的其他设备也访问不到。
确实需要局域网访问时可以显式放开：`HOST=0.0.0.0 bun run dev:server`（启动时会警告）。

具体来说，它**没有**：

- ❌ 登录与会话（任何能访问到端口的人都能看到全部训练数据）
- ❌ 多用户数据隔离（所有查询都是单用户假设）
- ❌ 公网 OAuth 回调（回调地址绑死 `127.0.0.1`，在服务器上无法完成授权）

所以：**不要把它部署到公网 IP 或反向代理后面再对外分享。**
要多人使用，请每个人各自在本机部署一份。

这在早期反而是优点——没有账号系统、没有数据库共享、没有数据外泄面，
每个人拿到手就是一份干净隔离的环境。

---

## 项目定位：这是数据看板，不是训练计划工具

**使用者有专职教练负责训练计划，本项目不产出训练计划。**

系统的职责边界：

| 会做 | 不会做 |
|---|---|
| 采集、清洗、呈现训练数据 | 安排周跑量与训练日程 |
| 解读数据里的规律与异常 | 指定强度课组数、配速、组距 |
| 用真实比赛做锚点算能力基线 | 规定减量节奏或赛前安排 |
| 赛前状态体检（负荷、结构、长距离） | 判断"这周该练什么" |
| 赛后分段复盘（对比历史） | 开训练处方 |

页面上出现的「影响因素」「历史表现」「配速提示」都是**事实陈述**，不是建议。
例如"历史表现：2/3 场后半程加速"是把你自己的数据摆出来，
而不是告诉你下次该怎么跑 —— 那是教练的事。

AI 分析（需自行配置模型，未配置时自动跳过）同样遵守这个边界：
它只解读数据，需要提建议时会注明"供教练参考"。

### 数据存在哪里

**不在项目目录里**，而在 `~/.coros-dashboard/`：

```
~/.coros-dashboard/
├── coros.db          # 你的全部训练数据（SQLite）
├── tokens.json       # 你的 COROS OAuth 凭证（权限 600，不要提交或分享）
└── probe/            # MCP 接口探针输出
```

这是刻意与代码分离的，两个原因：

1. **数据不可再生。** `node_modules` / `dist` 随时能重建，但 DB 删了就得重新同步，
   而 FIT 下载有每日限额，删掉的部分可能永远回不来。
2. **凭证不能进版本库。** `tokens.json` 是明文 OAuth token，
   放在项目目录里意味着一次 `git add .` 就会把它提交上去。
   放 `~/` 下的隐藏目录是 Unix 惯例（同 `~/.ssh`、`~/.aws`）。

`.gitignore` 里另有一层兜底规则（`*.db`、`tokens.json`、`.env*`），
即使将来改了数据目录也不会误提交。

想换位置就设环境变量：

```bash
COROS_DATA_DIR=/your/path/data bun run dev:server
```

### 数据来源与已知边界

| 项目 | 来源 | 可靠性 |
|---|---|---|
| 活动/配速/心率 | COROS MCP | 高（官方数据） |
| 训练海拔 | FIT 文件（每秒采样） | 高（实测，±5-10m） |
| 赛事路线爬升 | 30m DEM 反查 | 中（误差可达 ±50%） |
| 成绩预测 | 真实比赛锚点 + 训练状态 | 中（受训练执行影响） |

**关于路线数据**：OSM 缺少大量城市路段与赛事赛道要素，实测无法自动生成可靠路线
（详见 `server/src/geocode.ts` 顶部的说明）。可靠的路线数据只有两个来源：
**GPX 上传**（最准）或**人工核实的路书**。系统不会用同城其它赛事的路线顶替。

## 快速开始

### 前置要求

| 项目 | 要求 |
|---|---|
| **Bun** | 1.x（必需，项目用 `bun run` 脚本和 `bun:sqlite`）<br>安装：`curl -fsSL https://bun.sh/install \| bash` |
| **COROS 账号** | 需要有已同步过训练的高驰账号 |
| **网络** | 仅授权与同步时需要；之后看板可离线使用 |

> 首次同步会拉取每场训练的分圈数据，量大时耗时较长（1–2 分钟）。
> 官方对 FIT 下载有 50 次/24 小时限制，别反复重装重同步。

```bash
# 1. 安装依赖
bun install

# 2. 授权连接 COROS（会打印一个链接，浏览器登录后自动完成）
bun run auth

# 3. 拉取数据到本地 SQLite
bun run sync --days=120

# 4. 构建前端并启动
bun run build
bun run dev:server
```

打开 <http://127.0.0.1:43124>。

之后每次训练完，在看板「设置」页点一次「立即同步」即可。

### 每个使用者需要自己做的事

项目不含任何人的数据，所以第一次跑起来有几件事必须你自己配：

| 项目 | 说明 |
|---|---|
| **COROS 授权** | 必须跑 `bun run auth` 走一次 OAuth 换自己的 token。没有别人的 token 可用，这是设计上故意的。 |
| **心率档案** | 在「设置」页填静息心率（可选最大心率）。心率区间边界全部由这两个值算出 —— 留空则分别回退到「从历史分圈推算」和生理中位数。 |
| **AI 模型** | 不填也能用，只是没有 AI 分析功能。需要自备 API key。 |

### 比赛怎么登记

「赛事路线」页点「+ 添加赛事」或「修改」：

- **从已同步的训练里选比赛** —— 比赛当天在手表里就是一次普通训练，没有额外标记。
  选它会自动带出当天的日期和距离，之后这场比赛就能用那天的真实分段数据做复盘，
  而不是只有赛前填的目标成绩。
- 也可以**不关联、手填日期** —— 适用于还没跑的未来比赛，或当天训练还没同步到。
- **主观体感备注** —— 跑完才知道的东西：累不累、哪里抽筋、哪里不舒服、哪一段状态好。
  COROS 完全不记录这类数据，只有你知道，而它往往是解释客观数据的关键。

比赛日分析会把备注放在**分段数据之前**送给模型，让它先读体感再解读配速和心率 ——
「这段掉速了」对应到「这里开始抽筋」，比单看数字有用得多。
同时也要求模型**保持独立**：如果备注说很累但数据显示全程心率配速都稳，
要如实指出两者不一致，而不是强行把数据解释成很累。

心率区间边界**不写死任何人的数值**，而是由你的 HRmax 和静息心率按 HRR 百分比现算：

| 区间 | HRR 占比 |
|---|---|
| Z1 有氧耐力 | 59–74% |
| Z2 有氧动力 | 74–84% |
| Z3 乳酸阈 | 85–88%（仅 4% 宽） |
| Z4 速度耐力 | 89–95% |
| Z5 无氧动力 | >95% |

爬升代价系数（爬坡每 m/km 慢多少秒/km）同理，是从**你自己的历史分圈**
线性回归拟合出来的，不是套用通用常数。数据不够时自动降级为「不修正」。

> 为什么不用绝对心率边界：同样 140 bpm，对静息 49 的人是有氧中段，
> 对静息 75 的人已经是高强度。写死绝对值等于把一个人的心率刻度套给所有人。

## 日常使用

| 操作 | 位置 |
|---|---|
| 看周跑量 / 训练负荷 | 左侧「训练」 |
| 看单次训练的逐段配速心率 | 训练页表格点任意一行 |
| 让 AI 分析某一次训练 | 详情页最下方「AI 训练分析」 |
| 配置模型 / 手动同步 | 左侧「设置」 |

**AI 分析只针对你指定的那一次训练**，不会批量跑。一周跑 6 次，你只挑需要复盘的那 1–2 次。

## 比赛日分析（赛后复盘 / 赛前方案）

侧栏「比赛日」页。**填比赛日期，按日期自动切模式**：

| 条件 | 模式 | 干什么 |
|---|---|---|
| 日期已过 | 赛后复盘 | 真实逐公里数据 → 诊断执行问题 |
| 日期在未来 | 赛前方案 | 训练体检 + 掉速规律 → 给配速分段计划 |

**为什么不做成纯对话**：比赛日分析是结构化、可重复的 —— 同一场每次都应该产出同样完整的一份
（配速策略、心率漂移、和目标的差距）。用对话的话你得描述要什么，每次还不一样，
多半会漏掉「第 25km 后心率漂移」这类关键信号。看完报告可以**追问**，那是对话擅长的事。

### 赛后复盘的关键判据

**配速和心率谁在动，才知道是「跑崩了」还是「配速本来就该那么慢」**：

| 配速 | 心率 | 判定 | 含义 |
|---|---|---|---|
| 变慢 | 心率上升 | 疲劳型掉速 | 体能撑不住，**不可控** |
| 变慢 | 心率基本不变 | 配速型掉速 | 主动降速，**可控** |
| 变快 | — | 负分段激进型 | 后程加速，最后 5km 容易崩 |

还会从历史长距离训练里统计出**习惯性掉速点**（掉速开始的那个公里数中位数），
用来和这场做对照 —— 知道是老毛病还是新问题。

### 追问

报告生成后下面的输入框可以继续追问。模型能看到原始数据 + 之前的完整对话，
对话存在 SQLite 的 `ai_chat` 表，刷新不丢。

端点：`GET /api/race?date=&goal=`、`POST /api/ai/race`、`POST /api/ai/race/ask`、
`GET|DELETE /api/race/thread?date=`

## 马拉松备赛分析

侧栏「备赛分析」页。**只看最近 N 周**（4/6/8/12/16 周可选）——备赛决策关心当前状态，
半年前的跑量对「能不能跑进目标成绩」没有参考价值。填上比赛日期后，体检项会按剩余天数
自动切换视角：>60 天是爬坡期、21–60 天是上量关键期、8–21 天是赛前窗口、≤7 天切到减量视角。

体检项（判定标准是马拉松备赛的通行经验值，非官方标准）：

| 项目 | 达标线 | 依据 |
|---|---|---|
| 最长单次跑量 | ≥30 km | 比赛日最关键的一次性耐力考验 |
| 周跑量 | ≥45 km/周 | 业余马拉松跑者的有氧堆积需求 |
| 强度课密度 | ≥1.5 次/周 | 够刺激阈值又不堆积疲劳 |
| 训练频次 | ≥4 场/周 | 有氧基础的连续性 |
| 跑量波动 | 单周涨幅 ≤20% | 超 20% 是公认的伤病风险信号 |
| 比赛日 | 按时长切换 | 爬坡 / 关键 / 赛前 / 减量 |

点「AI 备赛分析」把最近 N 周的跑量、最长单跑、强度课、负荷波动和当前预测一起交给模型，
让它回答三个问题：能不能跑出目标成绩、最大短板是什么、这周怎么练。
系统提示词里明确要求「不建议加量过头」和「剩余 2–3 周要切到减量视角」。

端点：`GET /api/race-prep?weeks=8&raceDate=YYYY-MM-DD`、`POST /api/ai/race-prep`

## 白天 / 黑夜主题

左侧栏顶部有切换按钮。首次访问跟随系统外观（`prefers-color-scheme`），
手动切过一次之后就固定用你的选择，不再被系统设置覆盖。

实现要点：

- 所有颜色都走 `styles.css` 顶部的 CSS 变量，**组件里不允许写死 hex**。
  暗色在 `:root`，浅色在 `[data-theme="light"]` 覆盖同一组变量名。
- 浅色下柠檬绿 `#c6f24e` 在白底上不可读，浅色主题换成同色系的可读深橄榄绿 `#5a7d00`。
- 图表的渐变（配速快慢色、散点）用 `color-mix(in oklab, ...)` 在 CSS 里混色，
  端点色取自主题变量，所以换肤时图表颜色自动跟着变，不需要在 JS 里重算 rgb。
- `index.html` 有一段内联脚本先于 React 设置 `data-theme`，
  否则深色用户刷新时会先闪一下白底。
- 对比度实测：正文 16:1、次要文字 6:1+，两套主题都过 WCAG AA。

## 三种查看粒度

看板在「训练」页提供 **周汇总 / 场次 / 逐条** 三种粒度：

### 周汇总（点周跑量柱子进入）

**周跑量柱状图点进去的是「这一周」，不是其中某一次训练。**
柱子的语义是周总量，点它就该看周聚合，不能落到某一条记录上。

- 四个汇总指标：周总跑量 / 场次与最长单次 / 总时长与消耗 / 周均心率与负荷。
- **逐场跑量柱状图**：横轴是这一周里每天的训练，点柱子进入那一天所属的场次详情。
- **本周每日分布**：周一到周日逐日列出，没训练的日子明确标「休息」。
  这是为了看训练是怎么**分布**在这一周里的 —— 堆在同一天和摊匀是两回事。
- **本周全部场次**：周内每一场的明细，点行进场次详情，可以单独让 AI 分析那一场。

### 按场次（默认，推荐）

**同一天的多次记录合并成一场，一次性发给 AI。** 解决的是间歇训练被手表拆成多条记录的问题：
`1km×10 + 800m×10 + 400m×2` 可能是 22 条记录，合并后 AI 看到的是一整场训练的结构。

- 分组规则：**同一天 + 记录间隔 < 4 小时**。只用日期分组会把早晚各跑一次误并成一场，所以加了时间间隔。
- 会自动识别「组结构」：把距离与配速高度一致的连续记录归为一组，还原成 `1km×10组`、`800m×10组`。
  识别容差是距离 ±12%、配速 ±20%（实测能容纳 GPS 抖动，又不会把不同组误并）。
- 合并后给出全场总里程 / 总时长 / 加权平均心率 / 负荷合计，并画出**整场连贯曲线**：
  把一天的多条记录接到同一条累计时间轴（含组间休息）上，配速、心率的整场起伏和组间休息（曲线断开的缺口）一眼可见。
- 单次长距离跑只有 1 条记录，走的是同一条代码路径，不需要特殊处理。
- **只分析这一天**：不会把其它日期的训练喂给模型（一个刻意的设计取舍）。
  场次复盘要回答「这场训练本身说明了什么」，混入跨场对比会让结论跑偏。
  同理，恢复状态与体能基线按**场次当天**取值（`captured_at <= 当天 23:59:59`），
  不是取数据库里最新一条 —— 否则分析历史场次会拿到别的日期的数据却标成「当日」。
- **逐段爬升会进 prompt**：分段表的「爬升 / 下降」两列直接来自 COROS 分圈数据。
  这是判断「某段慢是上坡还是退步」的唯一依据，缺了它 AI 会把上坡一律判成掉速。

### 逐条

点开某一条记录看它自己的分圈明细和 AI 分析。

## 自建成绩预测（不依赖官方体能评分）

侧栏「自建预测」页的成绩是**完全基于你自己的训练数据**算出来的，不使用 COROS 的 VO₂max / 跑步等级。

### 算法四步

**1. 提取成绩锚点** —— 在每次训练的**连续分圈**内滑动，找出累计距离达标的最快窗口。
必须连续：间歇训练各组之间不会拼接，所以不会出现「10 组 ×1km 被当成 10 公里成绩」的假锚点。
同时过滤 GPS 噪声（配速不在 2:00–15:00/km 区间的段一律丢弃，典型数据集里会滤掉一两百段）。

**2. 反推阈值配速** —— 对「配速-心率」做回归，但**只取有氧区间（3:40–5:05）**。
心率在轻松配速上会压平（约 145 bpm 就到底），把轻松段算进去会把斜率压歪。
再取 88.5% 最大心率（Tanaka 公式推算）对应的配速作为阈值。
反推结果通常比 COROS 官方给的阈值配速略快（取自态度训练的数据点普遍比全力比赛保守）。

**3. 拟合个人 Riegel 指数** —— 理论值 1.06 是「两场全力比赛」的关系。
训练场上的最佳连续段强度不一致（5km 最佳常来自强度课，长距离最佳来自稳态跑），
所以先按「配速/阈值配速」把成绩分层，只在**同一强度层内**两两配对求 k。
拟合出的 k 一般在 1.05–1.15 之间，配对组数越少、四分位宽越大，k 越不可信。

**4. 多模型加权合成** —— 关键设计是**锚点可信度分层**：

| 层级 | 距离 | 为什么 |
|---|---|---|
| A | ≥15km | 训练强度≈比赛强度，外推最可信 |
| B | 8–15km | 中等可信，需要模型外推 |
| C | ≤5km | 训练里的短距离几乎不是全力，系统性偏保守 |

C 层不参与定区间；10K 锚点外推到全马时权重压到最低
（短距离配速比长距离快几十秒是正常的，强度本就不同）。
区间用**加权分位数**并设下限（短距离 ±2%、半马 ±2.5%、全马 ±3.5%），
避免两个模型凑巧接近时出现「7 秒宽」的虚假精度。

### 输出长什么样

跑完 `bun run sync` 后，「自建预测」页会用**你自己的训练数据**给出成绩预测，
格式如下（数字随各自的数据变化）：

| 距离 | 自建 | 配速 | 可信区间 | COROS 官方 | 差异 |
|---|---|---|---|---|---|
| 5 公里 | — | — | — | — | — |
| 10 公里 | — | — | — | — | — |
| 半程马拉松 | — | — | — | — | — |
| 全程马拉松 | — | — | — | — | — |

右侧的「COROS 官方」是设备自己给的成绩预测，可以拿来对照自建模型的偏差 ——
偏差小说明模型在你身上拟合得好，偏差大则要检查锚点选得对不对。

页面上每个数字都能展开，看到它由哪几个模型合成、权重多少、锚点是哪次训练。

算法测试：`cd server && bun run src/cli/test-prediction.ts`（40 项，含 Riegel/Daniels 已知值、
合成数据反推 k、噪声过滤、单调性、区间下限）

## 数据来源与已知边界

全部数据来自 COROS 官方 MCP，未使用任何非官方接口。

| 模块 | 状态 |
|---|---|
| 活动记录 / 单次详情 / 逐圈分段 | ✅ 完整 |
| 训练负荷（短期/长期/负荷比） | ✅ 完整 |
| 体能评估（VO₂max / 阈值配速 / 成绩预测） | ✅ 完整 |
| 恢复状态、日均压力、全天心率 | ✅ 可用 |
| 静息心率序列 / 睡眠 HRV / 压力分区 | ⚠️ 需要夜间佩戴手表才有数据 |
| 睡眠评分 | ⚠️ 同上，未佩戴的日期返回 -1 |
| FIT 原始文件 | 未接入（官方限制 50 个/24 小时） |

几个必须知道的技术细节，改动代码前请留意：

1. **MCP 返回格式是混合的**：概览类工具（`querySportRecords` / `getActivityDetail` 等）返回**可读文本**，
   时序类工具（`queryActivityLapData`）返回 **JSON**。解析层 `server/src/coros/parse.ts` 分别处理，
   并有断言用真实数据校验：`cd server && bun run src/cli/test-parse.ts`

2. **文本行内多个字段用 ` | ` 分隔**。`toRecord` 必须按管道切分；但按管道切分后，
   `endTimestamp=xxx` 会落到没有冒号的片段里，所以时间戳要**直接从整块文本正则抓**，别从 record 取。

3. **分圈距离原始单位是厘米**。除以 100000 才是公里；已在多次活动上与 COROS 记录的总距离交叉验证一致（不要用某一个人的具体数字做校验基准 —— 换个人就失效了）。

4. **`lapGroups` 是同一活动的多种粒度并存**（观察到 5km / 10km / 1km / 整段汇总四组），
   解析时取「圈数最多」的那一组 = 最细可用粒度。

5. **`startTs` / `endTs` 的单位是秒**，不是毫秒。再除一次 1000 会把 3354 秒变成 3 秒。

6. **同步必须用不重叠的窗口**。写成 `[now-offset, now]` 再用 `min(offset, 30)` 截断的话，
   每个窗口都等于「最近 30 天」，回溯天数完全失效。

8. **心率区间是本看板自己算的**（Tanaka 公式推算最大心率），COROS 未提供分区字段。
   界面上已标注口径，不要当作官方数据。

8. **Drizzle 必须用 `db.select()` 核心 API**。`db.query.*` 关系查询层在 bun-sqlite 驱动下
   不提供同步的 `.get()` / `.all()`，用了会在运行时报错。

10. **重启服务要按 PID 杀**。进程命令行只有 `bun run src/index.ts`（没有路径前缀），
   `pkill -f` 匹配不到残留进程，会导致旧代码继续占用端口。

**加一份迁移**：在 `server/drizzle/` 新建 `0010_你的说明.sql`，多条语句用
`--> statement-breakpoint` 分隔。服务下次启动会自动应用，执行过的记在库里
`_migrations` 表，不会重复跑。迁移是**手写**的 —— `server/drizzle.config.ts` 只是给
`drizzle-kit` 自己的 CLI（generate / push / studio）看的，**别用 `drizzle-kit generate`
生成迁移**，它按 schema 反推出来的 SQL 和这些已上线的迁移对不上。

## 安全

- OAuth token 存在 `~/.coros-dashboard/tokens.json`，权限 600，仅本机。
- 数据库 `~/.coros-dashboard/coros.db`。
- AI 的 API Key 由你自己填写，存在同一个本地数据库里。
- 服务只监听 `127.0.0.1`，不对外暴露。
